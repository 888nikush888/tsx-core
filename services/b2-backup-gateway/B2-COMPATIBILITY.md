# Disposable B2 compatibility acceptance

This is an **unexecuted** procedure for the actual VPS operator. Use a new private, Object Lock-enabled **disposable** B2 bucket in the intended region. Do not use the production bucket or master key. Keep credentials in the host's protected secret store; do not paste them into a ticket, command log, or report. Record only timestamps, HTTP status, version counts, checksums, and the disposable bucket identifier. A passing mock test is not evidence for this procedure.

Prerequisites: Node 22/npm 10, this exact candidate commit, a dedicated temporary directory owned by the gateway process with mode 0700, HTTPS certificate trusted by TSX Core, and an application key restricted to the disposable bucket and `tsx-core/` prefix. The key needs `listFiles`, `readFiles`, `writeFiles`, `readFileRetentions`, and `writeFileRetentions`; check Backblaze's `listAllBucketNames` compatibility requirement for restricted keys. Keep deletion permission on a **separate cleanup identity**, unavailable to the gateway. Install only with `npm ci` from the pinned lockfile and run `npm audit --audit-level=moderate`.

1. Prepare a small synthetic `.tgfb` with the `TGFE1\0` header and record its byte count and SHA-256. Use a fresh valid name such as `backup-2026-b2probe-<random>.tgfb`. Start the gateway with the disposable bucket and a short-lived random bearer token. Do not log that token.
2. Send PUT to `/objects/{artifact}` with `Content-Type: application/octet-stream`, exact `Content-Length`, and `X-Backup-SHA256`. Require HTTP 201 and a retention receipt at least 30 days beyond **response time**. Independently request B2 `ListObjectVersions`, version-pinned `HeadObject`, `GetObjectRetention`, and `GetObject`: require exactly one non-delete version, exact size/metadata SHA-256, COMPLIANCE mode, matching retain-until date, and exact downloaded bytes/hash. A missing field is a failure.
3. Send the identical PUT again. Require HTTP 200 with a valid retention receipt, exactly one B2 version afterward, and identical GET bytes. Send same name with different bytes/hash; require failure without receipt and no new version. Change the requested Content-Length, checksum, or magic separately; require failure without receipt and no new version.
4. Run two simultaneous **direct S3 conditional** `PutObject` requests for a different fresh key, each with `IfNoneMatch: *`, COMPLIANCE 31-day retention, and different bodies. Require exactly one success, one conditional failure, and exactly one listed version. Repeat at least ten times with fresh keys, including requests begun in the same second. If B2 ignores the condition, returns two versions, or rejects the condition as unsupported, block live use; do not remove the condition or version checks to make the test pass.
5. Simulate an ambiguous result on another fresh name: send a direct S3 PUT with the same size, SHA-256 metadata and 31-day COMPLIANCE retention, but deliberately discard its successful response. Then send the identical bytes through the gateway. Require safe HTTP 200 re-adoption, full version-pinned readback, a valid retention receipt, and exactly one B2 version. Send altered bytes and require failure. Repeat with a network drop during the gateway's first PUT; if the provider write completed, retry must re-adopt. If it did not, retry may create the only version. In both cases require one version and exact GET bytes.
6. Run TSX Core's actual encrypted backup PUT/GET/recovery round trip through the gateway on the VPS. Verify the downloaded SHA-256 and restored artifact evidence. Test one over-budget concurrent upload and one wrong bearer token; neither may write a B2 version. Confirm that no credential or bearer value appears in gateway, proxy, or system logs.
7. Record each test key and version ID in a protected cleanup ledger. COMPLIANCE retention prevents deletion before expiry. Schedule a follow-up after each retain-until date using the separate cleanup identity to delete **that exact version**, then re-list the key and require zero versions and zero delete markers. Do not use a bucket lifecycle rule that purges versions before the retention period. Confirm B2 billing/storage after cleanup.

Acceptance is bound to the exact service commit, B2 region and bucket configuration, application-key capability set, TLS endpoint, and VPS runtime. Any failed or skipped step keeps the gateway disabled. This test does not establish Google Drive secondary backup, alert delivery, audit separation, or production restore readiness.
