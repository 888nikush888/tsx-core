# B2 backup gateway candidate

This standalone HTTPS service implements TSX Core's `/objects/{artifact}` PUT/GET contract. It requires Node 22 and the pinned `@aws-sdk/client-s3` dependency. The encrypted `.tgfb` bytes are verified before upload; the gateway requests B2 Object Lock **COMPLIANCE** retention for 31 days and emits `X-Backup-Retention-Until` only after a version-specific HEAD confirms version, size and SHA-256 metadata and Get Object Retention confirms mode and date. GET selects the sole version, checks its lock, then downloads and hashes the exact bytes before serving them.

Create a private B2 bucket with Object Lock enabled. Use a bucket and prefix restricted application key with `listFiles`, `readFiles`, `writeFiles`, `readFileRetentions` and `writeFileRetentions`; Backblaze also advises `listAllBucketNames` for bucket-restricted keys used with SDKs. Do not give it `deleteFiles` or governance bypass capability. The gateway rejects names with existing versions and fails closed if another version appears. Keep one gateway process per prefix; the in-process lock prevents its own concurrent replay, while the B2 version count detects external races. An operational live B2 test must confirm that B2 honors `If-None-Match: *` for conditional PUT; this behavior is not documented in the B2 reference, so this candidate alone is **not live-ready**.

Set `B2_S3_ENDPOINT` to the regional `https://s3.<region>.backblazeb2.com`, `B2_S3_REGION`, `B2_BUCKET`, `B2_APPLICATION_KEY_ID`, `B2_APPLICATION_KEY`, `BACKUP_OFFSITE_TOKEN` (at least 32 characters), and `BACKUP_GATEWAY_TLS_KEY_FILE`/`BACKUP_GATEWAY_TLS_CERT_FILE`. Optional: `B2_OBJECT_PREFIX`, `BACKUP_GATEWAY_BIND`, `BACKUP_GATEWAY_PORT`, `BACKUP_GATEWAY_MAX_OBJECT_BYTES`. Install with `npm ci`, then run `node server.js`. Configure TSX Core's `BACKUP_OFFSITE_URL_TEMPLATE=https://<gateway>/objects/{artifact}` and `BACKUP_OFFSITE_RETENTION_DAYS=30`. Give TSX Core the CA certificate needed to trust the gateway's TLS certificate.

The gateway creates no DELETE route. Its temporary files contain already encrypted backup objects and are removed after each request. Put temporary storage on an encrypted volume with enough capacity for one maximum-size object. The HTTPS listener defaults to loopback for a reverse proxy or private tunnel; if exposed directly, restrict network ingress to the TSX Core host. This candidate caps a single object at 5,000,000,000 bytes, matching B2's standard upload limit; TSX Core permits larger encrypted objects, so backups above this cap require a separate multipart implementation and are rejected here.

No real B2 credentials or live bucket were used in the contract tests. Before production: prove Object Lock and version behavior against a disposable B2 bucket, confirm TLS and the TSX Core round trip on the actual VPS, and run restore drills. Google Drive secondary replication is separate work.
