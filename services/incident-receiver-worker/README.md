# External incident receiver candidate

This Cloudflare Worker is a **disabled candidate** for the external HTTPS endpoint consumed by `src/alert_relay.ts`. Its 20-alert/64 KiB acceptance limit does not yet match the existing sender's 100-alert/1 MiB contract; do not configure it as the production receiver until that mismatch is resolved and tested. The [full-contract blocker record](FULL-CONTRACT-BLOCKERS.md) details why raising two constants alone is unsafe. It accepts `POST /alerts` with the relay's Bearer token and exact `X-Alert-Source: tsx-core`, validates a bounded Alertmanager JSON envelope, and sends one plain-text Telegram Bot API message for a firing or resolved group. Only allowlisted labels enter the message: alert name, severity, service, and each supplied `correlation_id`. Annotations and the raw body are never forwarded to Telegram, written to D1, or logged. `GET /healthz` says only that the Worker process responds; host-down heartbeat monitoring remains a separate Healthchecks.io concern.

The candidate uses a D1 table with a unique HMAC delivery key. It reserves the key before contacting Telegram. A duplicate receives 202 only after a previous Telegram success and D1 confirmation. A concurrent, pending, or uncertain delivery receives 503 without another Telegram call. A verified Telegram 429 with `ok:false` and bounded `retry_after` is the sole automatic retry path. Successful writes are deduplicated for 20 minutes, allowing Alertmanager's current 30-minute reminder interval to send a fresh reminder. An unconfirmed network outcome or a failed post-send D1 commit remains blocked for manual reconciliation: Telegram has no idempotency key, so automatically retrying that state could send a duplicate. A 202 response never claims delivery merely because the Worker accepted a request.

## Operator preparation; no deployment performed

1. Create a Cloudflare Worker and D1 database, bind it as `DB`, then apply `schema.sql`. `wrangler.toml.example` has no real database ID and is intentionally nondeployable until filled by the operator.
2. Configure `RELAY_TOKEN`, `DEDUPE_SECRET`, and `TELEGRAM_BOT_TOKEN` as **Worker secret bindings**, not plaintext Wrangler `vars` or repository files. Set `TELEGRAM_CHAT_ID` as an environment binding scoped to the desired private chat. The first two secrets must be independent random values of at least 32 allowed characters. Keep the Telegram bot token and chat ID entirely off the VPS.
3. Set the VPS relay's `ALERT_WEBHOOK_URL` to the Worker's HTTPS `/alerts` endpoint and its `ALERT_WEBHOOK_TOKEN` secret to the same value as the Worker's `RELAY_TOKEN`. The existing relay supplies the Bearer header and `X-Alert-Source` and returns non-2xx to Alertmanager on failed delivery.
4. Review Alertmanager grouping before adoption. Its current `max_alerts: 100` and relay's 1 MiB input limit exceed this Worker's 20-alert/64 KiB limits. The Worker rejects oversized or truncated groups; it never claims partial success. Adjust and test the sender contract and alert volume before directing production traffic to it.
5. Name an on-call operator and verify an authorized synthetic firing/resolved alert end to end with the same `correlation_id`. This repository's offline tests do not establish that external delivery works.

For an `unknown` or stuck `pending` D1 row, inspect the delivery key and timestamp, check the Telegram chat for the corresponding notification, and make an explicit operator decision. Mark the row delivered only after confirming the message exists; remove it for retry only after proving no message was sent. Do not clear it based only on a timeout or HTTP status. The daily cron removes at most 1,000 expired **delivered** rows; it never erases unresolved outcomes.

The Worker runs without Node APIs or third-party packages. Offline contract tests: `node tests/test_incident_receiver_worker.js`. The test injects a fake Telegram fetch and fake D1 binding; it never calls Telegram. Real Cloudflare D1 concurrency, CPU use, Bot API delivery, and the Worker's public endpoint still require separate staging evidence. The `services/**` directory is outside the current `scripts/verify_exchange_implementation.js` source inventory, so integration also needs a deliberate source/release evidence decision.

As of 2026-09-25, [Cloudflare Workers Free limits](https://developers.cloudflare.com/workers/platform/limits/) include 100,000 requests/day and 10 ms CPU per HTTP request. [D1 Free limits](https://developers.cloudflare.com/d1/platform/pricing/) include 5 million rows read/day and 100,000 rows written/day; [the limits are enforced](https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/), so exhaustion makes this receiver return failure rather than claim a send. Cloudflare [secret bindings](https://developers.cloudflare.com/workers/configuration/secrets/) keep tokens out of source. The [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage) requires HTTPS and returns `ok` plus a sent message on success; this candidate requires a positive `message_id` before confirming delivery. Alertmanager's [webhook configuration](https://prometheus.io/docs/alerting/latest/configuration/#webhook_config) supports resolved notifications and bounded alert batches, while its retry behavior depends on a non-2xx response.
