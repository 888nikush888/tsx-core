# Full relay contract: adoption blockers and bounded path

This is an implementation decision record, not a deployment approval. The Worker remains disabled. It has not been exercised on Cloudflare or against Telegram.

## What the checked-in sender accepts

`src/alert_relay.ts` forwards the original JSON body when it has `status` of `firing` or `resolved`, an `alerts` array of **0 through 100** entries, and string `alertname` and `severity` labels on each alert. It allows a body of up to **1 MiB**. It imposes no length or character limit on those two labels or an optional `correlation_id`; it does not reject a positive `truncatedAlerts`. `monitoring/alertmanager.yml` sets `max_alerts: 100`. Alertmanager's documented behavior is to omit alerts above that maximum and report their count in `truncatedAlerts`. A downstream Worker cannot recover omitted alerts.

The candidate Worker deliberately accepts only 1 through 20 alerts, 64 KiB, safe short labels, and `truncatedAlerts: 0`. It therefore cannot yet be configured as this sender's production receiver. Do not interpret its local tests as a full-contract pass.

## Why increasing two constants is insufficient

- One sender-valid `correlation_id` can occupy almost the entire 1 MiB body. Telegram `sendMessage` allows only 4,096 characters, so a textual notification may need roughly 256 or more messages. Workers Free allows 50 external subrequests per invocation. Telegram advises at most roughly one message per second to one chat, and at most 20 per minute in a group. The checked-in runtime timeout is 10 seconds (configurable up to 60 seconds). One synchronous webhook invocation therefore cannot guarantee complete delivery of that payload through `sendMessage`.
- Multiple `sendMessage` calls would create a partial-delivery state. If a later call times out, Telegram's API offers no idempotency key that proves whether it posted. A blanket retry could duplicate already visible pages; a 202 after only the first page would falsely claim complete delivery. A per-page durable ledger and operator reconciliation would be necessary.
- Cloudflare Workers Free has a 10 ms CPU budget per HTTP invocation. Parsing a worst-case 1 MiB JSON body, producing a safe label-only rendering, and calculating an HMAC have not been measured on that platform. D1 Free permits 100,000 rows written per day; ledger inserts, updates, indexes, and retry traffic share that quota. Quota or CPU exhaustion must fail closed.
- A positive `truncatedAlerts` is already irretrievable information loss upstream, even if the Worker can send every alert in the received array. Accepting it as complete would hide that loss; rejecting it cannot cause Alertmanager to add the omitted alerts on retry.

## Route to a reviewable implementation

1. Fix the upstream no-loss contract first. Choose routing/grouping and sender bounds that guarantee each webhook body has at most 100 alerts, at most 1 MiB, and `truncatedAlerts: 0`, or change the relay and downstream bounds together. Add an end-to-end test for an overfull group; simply setting Alertmanager `max_alerts: 0` can make the relay reject larger bodies.
2. For the accepted 0–100 alerts, use **one** Telegram `sendDocument` call when a label-only text notification would exceed 4,096 characters. Attach a bounded UTF-8 text/JSON file with every received alert's `alertname`, `severity`, optional `service`, and optional `correlation_id`, including full values. Give the document a short firing/resolved caption and count. Reject any rendering that cannot fit the documented document limit before reserving the D1 key. This avoids page-by-page partial delivery and usually consumes one external subrequest. Keep the existing HMAC reservation, confirmed `message_id`, 429-only automatic retry, and unknown-outcome manual reconciliation.
3. Prove worst-case behavior on the intended Cloudflare Free account before enablement: 1 MiB with one long correlation ID, 100 alerts, escaped Unicode/control characters, 0 alerts, exact 1 MiB boundary, positive `truncatedAlerts`, repeated/resolved notifications, concurrent retries, Telegram 429, ambiguous upload/response, D1 failure, and elapsed CPU and delivery time. The 10-second default relay timeout and Free CPU budget must both pass with headroom. Use mock Telegram for routine tests and an explicitly authorized synthetic alert for live acceptance. No live test has been run here.
4. If the Free limits fail, use a paid Worker or an external durable receiver with a measured CPU budget. A queue may decouple the relay timeout only if the relay receives 2xx **after durable acceptance is a documented contract**, with independent dead-letter monitoring and an operator path for uncertain Telegram sends; otherwise keep returning non-2xx until delivery is confirmed.

Official limits: [Alertmanager webhook](https://prometheus.io/docs/alerting/latest/configuration/#webhook_config), [Telegram `sendMessage` and `sendDocument`](https://core.telegram.org/bots/api), [Telegram rate guidance](https://core.telegram.org/bots/faq), [Workers Free limits](https://developers.cloudflare.com/workers/platform/limits/), [D1 Free pricing and quotas](https://developers.cloudflare.com/d1/platform/pricing/).
