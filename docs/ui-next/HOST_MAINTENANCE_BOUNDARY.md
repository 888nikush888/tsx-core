# Host maintenance boundary at integration head `17abeb0f`

This is a source-scoped design and read-only audit, not an operator control or release sign-off. The companion [machine audit](inventory/host-maintenance-boundary.json) accounts for all 70 external controls and all six deployment catalog gaps at integration head `17abeb0f2655f3c05560d047cc0c8a046b92865f`. The earlier [PR-head evidence](../testing/host-maintenance-boundary-efbcb568.json) remains an archival snapshot of `efbcb568`; [current evidence](../testing/host-maintenance-boundary-17abeb0f.json) binds the 90/6/216 inventory and 96-path slice to this integration base. `tests/test_host_maintenance_boundary.js` checks exact membership and verifies that none was promoted to UI evidence. No production configuration, credentials, order routing, or host service was changed.

| Deployment catalog gaps | 6 | Two build-time values, published host ports, CPU, memory, and observed image digest remain `known-gap`; image selection and running digest are separate facts. |

The existing UI can show partial deployment observations, but it has no authenticated host-side apply authority. In particular, `docker-compose.monitoring.yml` mounts `monitoring/prometheus.yml` as a read-only **single file**, and the Prometheus command does not enable a reload endpoint. Replacing the host file atomically would leave that bind mount on the old inode; writing a Core setting would neither reload Prometheus nor prove its active value. Enabling an unauthenticated lifecycle endpoint on the current container network would create a new control path for other containers. These are blockers to presenting any monitoring setting as operable now. Similar host recreation, key custody, or build requirements block the other groups. A Core container must not receive the Docker socket, arbitrary host command execution, a TLS private key readback path, or an override for critical alert detections.

## First implementation slice: Prometheus scrape interval

Use `monitoring.prometheus.scrape_interval` as the first candidate because it is a bounded, nonsecret scalar with observable effect. It remains `unverified` until a separate host-plane implementation and an exact-release runtime test pass. The implementation should be a small, independently deployed maintenance service, with one allowlisted operation rather than a generic file editor or command API.

1. **Authority and request.** The existing browser session must be an administrator. A same-origin Core route accepts only `{ intervalSeconds, baseRevision, confirmation }`; validate an integer 10–30, reject unknown keys and stale revisions, and require an explicit confirmation. Core writes an `authorized` audit record before sending a typed request to a fixed maintenance-service origin over mutually authenticated TLS. The browser never supplies a target URL, filename, shell command, token, or certificate. The host service independently verifies Core's pinned client identity, a short deadline, a unique operation ID, the base hash, and the one allowed operation. Viewer and recovery-mode access are denied.
2. **Prepare and persist.** Move Prometheus configuration to a dedicated host-managed directory, mounted read-only as a directory into Prometheus and writable only to the maintenance service. Preserve the existing rules file and immutable alert definitions. The service parses the current file, changes exactly `global.scrape_interval`, rejects any other diff, writes a candidate with restrictive permissions, runs a fixed `promtool check config` invocation without a shell, and fsyncs both the candidate and a durable journal containing prior and proposed SHA-256 hashes. No arbitrary path is accepted.
3. **Apply and observe.** Atomically rename the candidate inside the mounted directory. A narrowly scoped helper sharing the Prometheus PID namespace, running under the same unprivileged UID, sends only `SIGHUP` to the pinned Prometheus process; it has no Docker socket and exposes no general signal command. Read the active configuration from Prometheus and require the requested interval and target health within a bounded deadline. The Core and host audits record the requested value, before/after hashes, active readback, actor, operation ID, and outcome, without embedding credentials or certificate bytes. The UI distinguishes *pending*, *active*, *rolled back*, and *manual recovery required*.
4. **Rollback and crash recovery.** On validation, reload, or health failure, atomically restore the journaled prior file, signal one more reload, and prove the old active value and target health. A crash-recovery worker reconciles journal, on-disk hash, and active config before admitting another change. If rollback proof fails, retain the incident state and block further edits; never claim success from a write or signal alone. A later admin rollback is a new audited operation using the same revision check.
5. **Proof required before promotion.** Cover bounds, unknown-key and stale-revision rejection, viewer denial, durable audit failure, exact-file diff, invalid YAML, symlink/path substitution, interrupted rename, failed reload, failed readback, failed rollback, retry idempotency, and recovery after restart. An isolated Compose run must show a browser-admin save becoming active in Prometheus, a synthetic scrape succeeding through the trusted CA, and a rollback restoring the prior interval. It must also show that Viewer and relay delivery remain isolated, with no real exchange credentials or order calls.

The service boundary itself needs a security review before implementation. The present repository has no such service, no configured client identity for it, no active-config attestation returned to Core, and no directory mount/reload helper. The design therefore does not change evidence statuses, add a browser button, or imply that host settings can already be applied safely.
