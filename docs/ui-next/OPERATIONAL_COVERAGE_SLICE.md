# Operational UI coverage: audited static slices

[The machine-readable slice](inventory/operational-coverage-slice.json) classifies 75 existing parameter contracts: 36 managed runtime settings, ten account fields, 22 Telegram Viewer fields, six deployment/build values and the mandatory protective-stop gate. It records the UI control, mutation route, validator, audit action and contract test for each writable group. The [regression test](../../tests/test_ui_operational_coverage.js) fails when a field in these audited families is added without classification or when a runtime-editable field lacks one of those references. The existing UI-register test separately checks that the generated parameter register matches source defaults.

Managed runtime settings can be saved in the UI but generally take effect only after restart. Account name, exchange and mode are set on creation; they are not editable bindings on an existing account. Account status, kill-switch state, version and credential fingerprint are evidence fields, with separate guarded commands where applicable. Build values, ports, resource limits and image digest remain host/bootstrap owned. The UI shows the effective browser basename, only a configured/not-configured flag for GTM, and partial listener/declaration/cgroup evidence for ports and resources; it does **not** show the running image digest or prove effective host bindings. Each of these six values retains an explicit `host-maintenance-ui` gap and needs an authorized maintenance path before UI-managed changes can be claimed. The protective-stop requirement remains a server-enforced gate.

The Telegram Viewer slice covers 21 editable settings and the fixed 24h time format as read-only evidence. Admin writes replace the complete validated settings document through a revision-bound route; the separate viewer service observes the persisted document. Bot/service tokens remain separate secret commands. The UI disables all settings inputs, token commands and test delivery for read-only operators; server authorization remains authoritative. The [viewer API test](../../tests/test_telegram_viewer_api.js) checks read, write, stale revision, role rejection and audit. The [display test](../../frontend/tests/telegram-viewer-display.test.tsx) checks a browser-form write and read-only controls. These are targeted contract and component checks, not end-to-end proof of every setting through a deployed browser and service restart.

This is deliberately a scoped inventory, not a 100% UI-coverage claim for the other parameter families, secrets, monitoring/backup host files or external provider settings. Those need their own audited slices before the broader Plan 005 coverage criterion can pass.
